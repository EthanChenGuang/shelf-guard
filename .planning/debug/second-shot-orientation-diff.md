root_cause: |
  code (primary, fixed here): In src/hooks/useCameraStream.ts, the effect that attaches the
  live MediaStream to the <video> element (`useEffect(() => { video.srcObject = stream; ... },
  [stream])`) depends only on the `stream` object's identity. App.tsx conditionally renders
  <CameraView> (which owns the sole <video ref={videoRef}> element) only when
  `appMode === 'CAMERA_IDLE'`, so CameraView — and its <video> DOM node — fully unmounts and
  remounts on every transition through ROI_CONFIG / SCANNING_ANIM / PROCESSING /
  RESULT_INSPECT and back. Because `stream` itself never changes identity across these
  remounts, the effect never re-fires for the freshly-mounted <video> node, leaving it
  permanently detached (videoWidth=0, srcObject=null) from the very first post-baseline
  return to CAMERA_IDLE onward — i.e. from the 2nd shutter press for the rest of the session.
  environment (contributing, not fixed — pre-existing, orthogonal): ImageCapture.takePhoto()
  bypasses the <video> element (reads the raw MediaStreamTrack directly), so it masks the dead
  <video> defect whenever it succeeds — but its still-photo output characteristics
  (resolution/native aspect, and cross-device orientation handling) differ from what the
  live-video/canvas fallback would have produced, per the team's own prior commit ed12492. This
  AND-gates with the code defect: the code defect forces every 2nd+ capture through
  ImageCapture exclusively (no possibility of correct canvas fallback), and wherever that
  path's output differs from the baseline's original video-derived framing (or is unavailable
  entirely, e.g. Safari/iOS), the result is either a misaligned/differently-cropped comparison
  photo (garbled diff, perceived "orientation flip") or — confirmed directly via falsification
  test — an indefinite UI hang (shutter permanently locked) when ImageCapture is unavailable.
fix: |
  Track the actual <video> DOM node in React state via a callback ref (in addition to the
  existing plain useRef used for synchronous reads elsewhere in the hook), and make the
  srcObject-attach effect depend on that state value (in addition to `stream`) so it re-fires
  whenever a new <video> element mounts — not only when the MediaStream identity changes. This
  restores the invariant the rest of the code already assumes: videoRef.current is always a
  live, stream-attached element whenever CameraView is mounted.
