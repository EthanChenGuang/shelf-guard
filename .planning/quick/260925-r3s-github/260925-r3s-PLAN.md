<objective>
Extend the existing capability-gated camera hook/view (not a third-party library — research
confirmed no evaluated library adds this) with tap-to-focus: detect `focusMode`/`focusDistance`
on the active `MediaStreamTrack` exactly like the existing `hasZoom`/`hasTorch` detection, and
when present, let the user tap a point on the live camera preview to apply a
`focusMode`+`pointsOfInterest` constraint at that point. On devices/browsers where the capability
is absent (all of iOS Safari, per the W3C implementation matrix), the control must not render,
must not attach any tap behavior, and must not throw.

Purpose: The project's camera capture was reported as "too weak"; research established the real
gap is that `useCameraStream.ts` already does the hard parts correctly (capability-gated
zoom/torch, `ImageCapture`-first capture with canvas fallback) but has never extended that same
pattern to focus. This closes that gap without swapping libraries or regressing any existing
capability.

Output: `useCameraStream` exposes `hasFocus`, `focusPoint`, `setFocusPoint(x, y)`; `CameraView`
attaches a tap listener to the existing shelf-swipe overlay layer that computes normalized tap
coordinates and forwards them via `onFocusPointChange`, and renders a focus reticle at the
tapped point — both gated on `hasFocus`; `App.tsx` wires the three together; two new test files
cover hook-level capability/constraint behavior and component-level tap/reticle behavior.
</objective>

# Existing zoom/torch capability-gated precedent to mirror exactly for focus (same file, same shape):
# - `useCameraStream`'s `startCamera()` already does, right after computing `capabilities`:
#     setHasTorch('torch' in capabilities);
#     if (capabilities.zoom && typeof capabilities.zoom.min === 'number' && ...) { setHasZoom(true); ... } else { setHasZoom(false); ... }
#   Focus detection follows the identical cast-and-check pattern in the same block, reading
#   `focusMode` (a `string[]` of supported modes, e.g. `['continuous','manual','single-shot']`
#   on Android Chrome) and `focusDistance` (a `{min,max,step?}` range, only present alongside
#   `manual` mode on real devices) instead of a `zoom`/`torch` key.
# - `setZoomLevel(value)` already does: capability check -> bail silently if unsupported ->
#   `await track.applyConstraints({advanced: [{zoom: value} as MediaTrackConstraintSet]})` inside
#   try/catch -> `setCurrentZoom(value)` only on success -> `console.warn('Zoom constraint
#   failed:', e)` on catch. `setFocusPoint(x, y)` mirrors this exactly: constraint payload is
#   `{focusMode: mode, pointsOfInterest: [{x, y}]}` where `mode` is `'single-shot'` if the
#   device supports it (preferred — a one-shot refocus at the tapped point, not a persistent
#   manual override) else `'manual'`.
# - `stopCamera()` already resets `hasTorch`/`isTorchOn`/`hasZoom`/`zoomLevels`/`currentZoom` to
#   false/[]/null when the stream tears down — `hasFocus`/`focusPoint` must reset the same way.
# - `startCamera()`'s no-track `else` branch resets all capability flags to false — extend it too.
# - CameraView's `swipeLayerRef` div (`data-testid="shelf-swipe-layer"`, full-viewport overlay
#   above the video) already has `attachShelfSwipe()` (from `src/lib/shelfSwipe.ts`) wired to its
#   `pointerdown`/`pointerup` events for swipe-to-change-shelf, using a 50px move threshold
#   (`SWIPE_THRESHOLD_PX`). A second, independent `pointerdown`/`pointerup` listener pair on the
#   SAME element for tap-to-focus does not conflict — both listeners fire on the same events; use
#   a much smaller move threshold (e.g. 12px) so a real tap (still, or moves < 12px) triggers
#   focus while an intentional swipe (>= 50px) never does, and movements in between trigger
#   neither (safe dead zone, not a bug).
# - `MediaTrackCapabilities`/`MediaTrackConstraintSet` in this project's TS lib (target ES2022 +
#   DOM) do NOT include `zoom`/`torch`/`focusMode`/`focusDistance`/`pointsOfInterest` — this is
#   exactly why the existing code casts capabilities to `Record<string, unknown>` and casts
#   constraint objects `as MediaTrackConstraintSet`. Use the identical casting style for focus,
#   do not attempt to extend the global DOM lib types.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser `MediaStreamTrack.getCapabilities()`/`applyConstraints()` -> App | The `focusMode`/`focusDistance` capability shape and the tapped `pointsOfInterest` value are trusted browser/device-reported input this feature reads and re-applies; a malformed or unexpected shape must degrade to "no tap-to-focus" rather than crash the camera view |
| User tap on live camera preview -> `applyConstraints({advanced:[{focusMode, pointsOfInterest}]})` -> physical camera hardware | Tapped screen coordinates are normalized against the actual overlay's bounding rect and clamped into `[0, 1]` in `CameraView` before ever reaching `onFocusPointChange`/`setFocusPoint`, so the hardware never receives an out-of-bounds focus point |
